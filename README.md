# DevOps App Build Guide

A beginner-friendly reference repository for building and running **React, Node.js, Python, and Java** applications on **Windows and Ubuntu**, then containerizing each application with Docker.

The examples are intentionally small so you can focus on the developer workflow that a DevOps engineer needs to understand.

# 2. React application

React is a JavaScript library for building user interfaces. This example uses **Vite** to provide the development server and production build.

### Project files

- `package.json`: project metadata, dependencies, and npm scripts.
- `index.html`: HTML page used as the entry point by Vite.
- `src/main.jsx`: starts the React application and attaches it to the HTML page.
- `src/App.jsx`: contains the UI component.
- `node_modules/`: downloaded packages (created by `npm install`; do not commit it).
- `dist/`: production build output (created by `npm run build`).

### Windows (PowerShell)

Run these commands from the `react` directory:

```powershell
cd react
node --version
npm --version
npm install
npm run dev
```

Open the local URL printed by Vite, usually `http://localhost:5173`.

Build for production:

```powershell
npm run build
```

Preview the production build locally:

```powershell
npm run preview
```

### Ubuntu

Run these commands from the repository root:

```bash
cd react
node --version
npm --version
npm install
npm run dev -- --host 0.0.0.0
```

Open the URL printed by Vite. To create and preview a production build:

```bash
npm run build
npm run preview -- --host 0.0.0.0
```

### What do the commands mean?

| Command | Explanation |
|---|---|
| `npm install` | Reads `package.json` and installs the project's dependencies into `node_modules`. |
| `npm run dev` | Runs the `dev` script defined in `package.json`. |
| `npm run build` | Runs the production build script; Vite writes optimized files to `dist/`. |
| `npm run preview` | Serves the production build locally for testing. |

### React Dockerfiles

- `Dockerfile`: single-stage image. Node installs dependencies, builds the React app, and the same image serves the generated `dist` files using `serve`.
- `Dockerfile.multistage`: first stage builds the app with Node; the final Nginx stage serves only the static build output. This usually produces a smaller production image.

From the `react` directory:

```bash
# Single-stage image
docker build -f Dockerfile -t hello-react:single .

# Multi-stage image
docker build -f Dockerfile.multistage -t hello-react:multi .

# Run either image
docker run --rm -p 8080:80 hello-react:multi
```

Open `http://localhost:8080`.

# 3. Node.js application

Node.js runs JavaScript outside the browser. This example creates a small HTTP server using Node's built-in `http` module, so no external package is required.

### Project files

- `package.json`: project name, version, scripts, and dependency metadata.
- `app.js`: application source code.
- `package-lock.json`: exact dependency tree generated by npm when dependencies are installed.
- `node_modules/`: installed dependencies, if any.

### Windows (PowerShell)

```powershell
cd nodejs
node --version
npm --version
npm install
npm start
```

Open `http://localhost:3000`.

### Ubuntu

```bash
cd nodejs
node --version
npm --version
npm install
npm start
```

Open `http://localhost:3000`.

### What do the commands mean?

| Command | Explanation |
|---|---|
| `npm install` | Installs dependencies and creates/updates `package-lock.json`. This example has no third-party runtime dependencies. |
| `npm start` | Runs the `start` script from `package.json`, which executes `node app.js`. |
| `node app.js` | Runs the JavaScript file directly without using an npm script. |

### Node.js Dockerfiles

- `Dockerfile`: single-stage image with Node.js, application files, and runtime.
- `Dockerfile.multistage`: separates dependency installation from the final runtime image and copies only the required files.

From the `nodejs` directory:

```bash
docker build -f Dockerfile -t hello-node:single .
docker build -f Dockerfile.multistage -t hello-node:multi .
docker run --rm -p 3000:3000 hello-node:multi
```

Open `http://localhost:3000`.

# 4. Python application

Python is an interpreted programming language. This example uses Flask to expose a simple HTTP endpoint.

### Project files

- `app.py`: Python application source code.
- `requirements.txt`: list of Python packages and versions required by the application.
- `.venv/`: optional local virtual environment (created on your machine; do not commit it).
- `__pycache__/`: Python bytecode cache (do not commit it).

### Windows (PowerShell)

```powershell
cd python
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python --version
python -m pip install --upgrade pip
pip install -r requirements.txt
python app.py
```

Open `http://localhost:5000`.

If PowerShell blocks virtual-environment activation, you can run this for the current terminal session:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

Alternatively, skip activation and call the virtual environment's Python executable directly:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

### Ubuntu

```bash
cd python
python3 -m venv .venv
source .venv/bin/activate
python3 --version
python3 -m pip install --upgrade pip
pip install -r requirements.txt
python app.py
```

Open `http://localhost:5000`.

If `venv` is unavailable on Ubuntu, install the matching package for your Python version (for example, `sudo apt install python3-venv`).

### What do the commands mean?

| Command | Explanation |
|---|---|
| `python -m venv .venv` | Creates an isolated Python environment in `.venv`. |
| `source .venv/bin/activate` | Activates the environment on Ubuntu. |
| `.\.venv\Scripts\Activate.ps1` | Activates the environment in Windows PowerShell. |
| `pip install -r requirements.txt` | Installs every package listed in `requirements.txt`. |
| `python app.py` | Executes the Python application. |

### Python Dockerfiles

- `Dockerfile`: single-stage image that installs packages and runs the application.
- `Dockerfile.multistage`: installs packages into a virtual environment in a builder stage, then copies that environment into a clean Python runtime stage.

From the `python` directory:

```bash
docker build -f Dockerfile -t hello-python:single .
docker build -f Dockerfile.multistage -t hello-python:multi .
docker run --rm -p 5000:5000 hello-python:multi
```

Open `http://localhost:5000`.

# 5. Java application (Maven)

Java source code is compiled into bytecode and runs on the Java Virtual Machine (JVM). This example uses **Maven** to compile and package a simple application into a JAR file.

### Project files

- `pom.xml`: Maven Project Object Model. It defines project coordinates, Java version, dependencies, plugins, and build configuration.
- `src/main/java/`: standard location for application source code.
- `target/`: Maven build output directory (created during the build).
- `App.java`: Java application entry point; its `main` method is executed.

### Windows (PowerShell)

```powershell
cd java
java -version
mvn -version
mvn clean
mvn compile
mvn package
java -jar target/hello-java-1.0.0.jar
```

### Ubuntu

```bash
cd java
java -version
mvn -version
mvn clean
mvn compile
mvn package
java -jar target/hello-java-1.0.0.jar
```

### What do the commands mean?

| Command | Explanation |
|---|---|
| `mvn clean` | Deletes the previous Maven build output, normally the `target/` directory. |
| `mvn compile` | Compiles application source code. |
| `mvn package` | Compiles and packages the application into a JAR file. |
| `java -jar ...` | Runs an executable JAR using the JVM. |

### What is `pom.xml`?

`pom.xml` is Maven's project configuration file. Important elements in this example:

- `groupId`: identifies the project or organization namespace.
- `artifactId`: project/artifact name.
- `version`: project version.
- `properties`: shared build settings, such as the Java release version.
- `build/plugins`: Maven plugins that control tasks such as compilation and packaging.

### Java Dockerfiles

- `Dockerfile`: single-stage image uses a Maven/JDK image to build and run the application.
- `Dockerfile.multistage`: Maven/JDK builder compiles the JAR; a smaller JRE image runs it.

From the `java` directory:

```bash
docker build -f Dockerfile -t hello-java:single .
docker build -f Dockerfile.multistage -t hello-java:multi .
docker run --rm hello-java:multi
```

# 6. Docker concepts to understand

## What is a Dockerfile?

A Dockerfile is a text file containing instructions Docker uses to build an image. Common instructions:

| Instruction | Purpose |
|---|---|
| `FROM` | Selects the base image. |
| `WORKDIR` | Sets the working directory inside the image. |
| `COPY` | Copies files from the build context into the image. |
| `RUN` | Executes a command while building the image. |
| `EXPOSE` | Documents the port the application listens on; it does not publish the port. |
| `ENV` | Sets environment variables. |
| `CMD` | Defines the default command when a container starts. |
| `ENTRYPOINT` | Configures the main executable for the container. |

## Single-stage vs multi-stage builds

**Single-stage build:** all build tools, dependencies, and application files are kept in one image. It is straightforward to understand, but the final image can be larger.

**Multi-stage build:** uses multiple `FROM` stages. Build tools are used in an earlier stage, and only the required runtime files are copied into the final stage. This often reduces image size and attack surface.

## Useful Docker commands

```bash
# Build an image
docker build -t image-name:tag .

# List local images
docker images

# Run a container
docker run --name my-container -d -p 8080:80 image-name:tag

# List running containers
docker ps

# List all containers
docker ps -a

# View container logs
docker logs my-container

# Open a shell inside a running container (if the image contains a shell)
docker exec -it my-container sh

# Stop and remove a container
docker stop my-container
docker rm my-container

# Remove an image
docker rmi image-name:tag
```

The final `.` in `docker build` means the current directory is the build context. Docker can access files in that context, subject to `.dockerignore`.

## Why use `.dockerignore`?

It prevents unnecessary files (such as `.git`, `node_modules`, `.venv`, and build output) from being sent to the Docker build context. This can make builds faster and avoid copying local machine files into images.

# 7. Suggested DevOps practice

Try this sequence for each codebase:

1. Run the application locally on Windows or Ubuntu.
2. Identify its dependency file (`package.json`, `requirements.txt`, or `pom.xml`).
3. Build the application and identify its output (`dist/`, or `target/*.jar`).
4. Build and run the single-stage Docker image.
5. Build and run the multi-stage Docker image.
6. Compare image sizes using `docker images`.
7. Push the source code to GitHub.
8. Later, create a CI pipeline to install dependencies, test, build, scan, and publish the Docker image.

## Suggested Git commands

Run from the repository root:

```bash
git init
git add .
git commit -m "Add application build and Docker examples"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/devops-app-build-guide.git
git push -u origin main
```

Replace `YOUR-USERNAME` with your GitHub username and create the empty GitHub repository first.

## Learning outcome

After practising this repository, you should be able to explain the basic developer workflow:

**Source code → Dependencies → Build → Package → Docker image → Container**

That workflow is a foundation for CI/CD with Jenkins or GitHub Actions, image registries such as Docker Hub or Amazon ECR, and deployments to Kubernetes.
